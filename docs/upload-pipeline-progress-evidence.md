# Concurrent upload planning and progress

## Production trigger and preserved guarantees

The v0.8.0 external-drive Smart merge qualification on 12 October 2026 completed
1,821 files / 36.0 GiB in about 24 minutes 49 seconds, with zero failures or
replica restarts. Local checking held the upload at zero confirmed bytes for
approximately four minutes. The UI then showed zero completed files until the
final publication. Its ETA mixed per-file and cohort rates and changed rapidly.
This change repairs those client mechanisms. It leaves canonical schema 012,
provider APIs, atomic namespace publication, checksums, owner scoping, stale
snapshot denial, idempotency, source bounds and recovery guarantees unchanged.
There is no durable-schema migration.

## Selected pipeline and alternatives

Size planning first releases unambiguous files. Folder directories are prepared
before the first snapshot instead of making the whole folder wait for hashing.
Two existing fingerprint workers continue reading bounded chunks while the
existing source reader sends cleared files. Completed fingerprints accumulate
at the 100-task pool bound, or become eligible after the existing 15-second
progress window, or drain when hashing finishes. No unfinished fingerprint can
block every other readable file indefinitely.

Each ready group refreshes its size snapshot and completes exact reads and reuse
against that snapshot. A short tab-local namespace turn coordinates directory
preparation, those control requests, and upload publication. It never encloses
source reads or hashing. This avoids conflicts generated by the tab itself;
server root validation and source/target logical versions remain the security
and concurrency boundaries for other tabs and replicas. A changed or collected
snapshot still conflicts and safely replans. Completed fingerprints are reused
only while the same in-memory File remains bound; source reacquisition retains
the existing mandatory rehash rule.

Rejected alternatives are disabling stale-token validation, allowing a file to
transfer before its duplicate decision, hashing every file before starting any
transfer, and publishing each individual file. The first two weaken guarantees;
the third prevents overlap; the last adds unnecessary metadata commits. The
selected design coalesces the metadata operations while overlapping the slow
local and network stages. Concurrent disk reads compete for source bandwidth,
so faster wall time on a particular external disk remains a live qualification,
not a claim from local protocol tests.

## Progress and estimation

One reserved three-pixel track layers checking in Primary behind acknowledged
upload progress in Foreground: blue and white in the built-in dark theme, with
readable semantic contrast in light/custom themes. Both are independently named
accessible progress elements, with textual percentages; color is not the only
signal. Checking advances with completed local hash chunks or unambiguous
metadata decisions. Exact/reuse decisions may still be pending after local
checking reaches the end. Reuse/skip retains the existing resolved-transfer
progress semantics. Source reads never become provider-acknowledged bytes.
Keep-both shows no checking layer. Progress-only updates preserve row geometry,
focus, scroll anchoring and the bounded virtualized transfer list.

Directory/session preparation is reported as preparation; it is not an ETA
calculation job. ETA is an evolving conditional estimate over remaining declared
bytes, including not-yet-resolved candidates. Reuse can reduce that work. It uses
one cohort acknowledgement model, a 15-second window and time-based smoothing,
not a sum of per-file reciprocal durations. Startup remains provisional until
three measurement ticks, at least two acknowledgements and the smaller of one
source chunk or the remaining work have been observed within the current window.
Tiny late acknowledgements cannot reuse an earlier bulk sample's qualification.
Numeric ETA changes at most
once per five seconds. A stale acknowledgement window shows a nonnumeric phase
and zero current rate instead of extrapolating a huge remaining duration.
Per-file rows show operational phases, not competing unstable ETAs. The header
reserves enough width for 100%.

## Incremental publication and provider economics

Verified work becomes eligible after 15 seconds measured from its own readiness,
even if other files continue acknowledging data, or at one 1,000-item durable
progress segment, or when active data tasks drain. Each selected completion
batch keeps its stable transaction key and order before its first request.
Counts increment only after successful verified atomic publication; retries do
not announce false completion. One coalesced refresh updates the current folder
or an ancestor after publication. The deadline is eligibility, not a promise
that a failed provider or control request completes within 15 seconds.

The unchanged regional-standard-flat offline fixture measured the following
2,001-item completion alternatives. Empty file bodies isolate metadata/provider
economics; they are not throughput or photo-memory evidence.

Immutable-object and head PUT counts are 4, 6 and 42 respectively. Incremental
publication deliberately spends extra metadata traffic and retained history
for timely visibility; it is not an efficiency improvement over one end-of-burst
commit. Each file is verified exactly once, with no file-body reads/copies.
Actual deadline-driven batch sizes depend on source and network rate. Existing
single-transaction lifecycle and planning ratchets remain executable and
unchanged. New named incremental workloads and exact append-only ratchets cover
the two measured partial-publication cases; no supersession shim, exemption or
historical fixture rewrite is used. The 100-task admission limit, 32 MiB source
buffer, two independent bounded hash workers and 2,001-item lifecycle scale
qualification are preserved.

## Acceptance evidence

- Held fingerprint with a unique upload: original production source fails with
  the hash demonstrably held and zero confirmed bytes. The candidate uploads and
  publishes the unique file, resolves a ready ambiguous file, and safely reuses
  the held file after an intervening namespace change.
- Layered bars occupy identical geometry while checking leads upload progress.
- Original rate/ETA functions fail the controlled tiny-ACK and 200 ms cadence
  test; the candidate keeps startup provisional, holds the numeric estimate,
  ages stalled rate to zero, and fully displays 100%.
- Publication during continuing acknowledgements uses real held provider chunks
  plus the injected measurement clock. Existing stalled-source, cancellation,
  unreadable-source and original-session recovery qualifications remain required.
- Exact provider comparison preserves one verification per file and records
  complete count, cost, modeled latency/depth and metadata-byte tradeoffs.

CSP image warnings are excluded at the user's explicit instruction. No CSP or
bucket policy changes are included. No live production state was edited.
Post-release external-drive qualification remains necessary to measure overlap
under real disk contention, and Chrome total memory remains a separate finding.
