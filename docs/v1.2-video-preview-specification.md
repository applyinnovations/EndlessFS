# EndlessFS v1.2 Video Preview Profile Specification

**Status:** Deferred draft; revise after v1.1 implementation  
**Audience:** Implementation agents, maintainers, operators, reviewers, and security testers  
**Normative language:** “MUST”, “MUST NOT”, “SHOULD”, and “MAY” are requirements terms.  
**Target release:** v1.2  
**Inherits:** [`v1-specification.md`](./v1-specification.md) and [`v1.1-media-preview-specification.md`](./v1.1-media-preview-specification.md)

---

## 1. Executive contract and precedence

EndlessFS v1.2 adds an optional video-generation profile to the v1.1 preview architecture. It creates static representative poster images and bounded descriptive video metadata. It does not transcode, rewrite, stream, or create alternate playable video renditions.

This document is a delta specification. Every v1 and v1.1 requirement continues to apply unless this document explicitly extends it for video. The image-only base container remains a supported v1.2 deployment and MUST NOT acquire video dependencies.

Video capability is packaging-dependent. Official profiles use the same configuration schema, providers, preview-store layout, and application state. Before switching to an image-only container, an operator MUST remove `video` from `ENDLESSFS_PREVIEW_FORMATS`; leaving it configured is a startup error. Profile switching requires no state migration, bucket rewrite, or regeneration of image previews.

---

## 2. Scope

v1.2 includes:

- a separately packaged video generator and its pinned runtime dependencies;
- static representative video posters written through the v1.1 artifact-store contract;
- WebP-only output using the configured v1.1 resolution variants;
- safe metadata including duration and decoded display dimensions where available;
- explicit original-video playback in the full-viewport viewer through a fresh exact-version range-capable provider capability;
- automatic and explicit generation governed by the v1.1 policy and resource model;
- capability discovery and strict startup validation so the browser/API schema is unchanged while configuration must match the selected build;
- deterministic local fixtures and a packaged video-runtime test double or pinned test runtime; and
- independent OCI and release outputs with size, dependency, license, and vulnerability evidence.

v1.2 does not include:

- video transcoding, resizing of playable video, streaming playlists, adaptive bitrate output, subtitles, speech extraction, waveform generation, content analysis, or thumbnails for every scene;
- remote codec services, runtime-downloaded codecs, host-installed codec assumptions, GPU requirements, or arbitrary operator commands;
- automatic playback or retrieval of an excluded source;
- generated PDF previews, which are specified for v1.3; or
- search. Search remains a future feature independent of this delivery.

## 3. Build and container outputs

v1.2 adds:

| Nix output | Packaged capabilities | Required contents |
|---|---|---|
| `.#container` | `image` | The v1.1 minimal base; no video runtime or video-only libraries. |
| `.#container-images` | `image` | Explicit image-only alias. |
| `.#container-video` | `image,video` | The same Go application and assets plus the pinned closed video runtime. |
| `.#release-video` | `image,video` | Video-profile binary/OCI artifacts and complete dependency evidence. |

The video container MAY contain pinned native codec binaries or shared libraries required for safe video inspection and frame decoding. They are an explicit exception to the base image’s single-file contents, not permission to add application code in another language. The application, policy, orchestration, protocol, validation, and tests remain Go. The specialized image still MUST NOT contain a shell, package manager, compiler, source tree, mutable plugin directory, or runtime installer.

Video dependencies:

- are selected at build time from locked Nix inputs;
- have fixed application-owned invocation or linking behavior;
- cannot be replaced through environment variables, paths, uploaded files, themes, or provider data;
- run with bounded time, memory, input, output, file-descriptor, and process limits;
- receive no primary or preview provider credentials;
- receive only exact short-lived source/output capabilities or protected streams;
- perform no network request except to those exact capability origins where the implementation uses capabilities;
- are included only in profiles declaring `video`; and
- are inventoried with versions, licenses, source hashes, vulnerability results, and compressed/unpacked image-size deltas.

The v1.2 release MUST publish both image-only and video-enabled container outputs. Pulling the video image is the only supported way to add its codec runtime; startup never downloads dependencies.

## 4. Capability and configuration compatibility

The v1.1 environment schema is unchanged. `ENDLESSFS_PREVIEW_FORMATS` recognizes `video` in every official build.

- In `container-video`, configured `video` is active after the packaged generator and dependency integrity checks pass.
- In an image-only container, explicitly configured `video` is a startup error.
- A video file uses `icon.file.video` when `video` is not configured, without retrieving the original or looking up video artifacts.
- Missing, stale, corrupt, or lifecycle-deleted video artifacts in an active video profile fall back to `icon.file.video` at request time and may be regenerated according to policy.
- Switching profiles requires an accurate `ENDLESSFS_PREVIEW_FORMATS` value but no database migration, bucket rewrite, or reprocessing of image artifacts.

The public configuration reports packaged and active preview capability names. Startup guarantees configured and active capability sets are equal.

## 5. Supported input and validation

The video profile MUST support at least:

- ISO Base Media File Format video reported as `video/mp4` with an allowlisted packaged decoder; and
- WebM reported as `video/webm` with an allowlisted packaged decoder.

Container recognition, track structure, and codec support are separate decisions. A matching extension or client-supplied media type is never sufficient. The source provider’s validated type is a preliminary signal; the video worker independently verifies the container signature and selected track before decoding.

The capability manifest lists the exact container/codec combinations packaged in that image. Unsupported codecs in an otherwise recognized container produce a file-type icon and safe metadata explanation. They do not cause a generic file error or broaden the runtime dynamically.

The generator rejects or safely terminates on:

- malformed, truncated, cyclic, deeply nested, or inconsistent container metadata;
- declared durations, dimensions, frame rates, track counts, sample tables, or offsets outside hard limits;
- audio-only files presented as video;
- unsupported/encrypted tracks;
- excessive decoded dimensions or pixel counts;
- decompression bombs and resource exhaustion;
- a source change during ranged reads;
- codec process crash, timeout, unexpected output, or extra files; and
- any attempt by media metadata to name a path, URL, external resource, command, or output destination.

Embedded titles, comments, location, camera identity, creation software, and other source metadata are not copied to artifacts or public preview metadata.

## 6. Poster selection and metadata

Poster selection MUST be deterministic for a fixed source version and recipe.

The default recipe:

1. reads bounded container metadata and identifies the primary display video track;
2. computes bounded candidate timestamps near 10%, 50%, and 90% of duration, excluding the first and last 500 ms where duration permits;
3. seeks only through exact-version bounded range reads;
4. decodes at most three candidate frames within the operation resource budget;
5. rejects frames that are effectively blank or invalid using a documented deterministic luminance/variance threshold; and
6. selects the earliest remaining candidate with the highest deterministic visual-information score, falling back to the first successfully decoded frame.

For very short or duration-unknown video, the recipe selects the first successfully decoded nonblank frame within the bounded inspection window. Failure to find a frame produces `failed` or `unsupported` preview state and the video icon; it never retrieves the entire source without a configured hard bound.

The selected frame is normalized for coded/display rotation and pixel aspect ratio. The video recipe encodes it as static lossy WebP at quality `78` through the single pinned v1.2 encoder. Output uses the requested 256, 512, or viewer maximum edge and preserves the video's display aspect ratio without crop, stretch, or padding in the artifact. No audio is decoded unless the selected packaged library requires bounded demuxing, and audio bytes never appear in output.

Safe optional manifest metadata is:

```text
durationMilliseconds
displayWidth
displayHeight
```

Duration is a bounded non-negative integer derived from validated container/track timing. Filename, title, location, device, author, creation software, arbitrary tags, raw codec-private data, and full source track metadata are not returned.

## 7. Browser behavior

Video tiles use `icon.file.video` until a ready poster capability is available. Lazy automatic requests obey the v1.1 viewport, recency, size, format, and concurrency rules.

The full-viewport viewer:

- shows the ready poster immediately where available;
- shows duration and dimensions where safely available;
- provides explicit Play original and Download actions;
- creates a fresh exact-path/version inline capability only after Play original is activated;
- uses a native application-owned `<video controls>` element with preload `metadata` or `none`, never autoplay;
- supports provider range requests and capability refresh after reauthorization;
- adds only explicit provider origins to `media-src` and `connect-src`;
- supplies application-owned labels, fallback text, keyboard behavior, and focus management; and
- falls back to the poster/icon plus Download when the browser or codec cannot play the original.

Automatic poster generation and metadata display never imply that the original is browser-playable.

## 8. Security and runtime isolation

The video decoder is a hostile-input boundary. The implementation MUST prefer a one-operation worker process so decoder crashes and malformed-media exits cannot terminate the control server.

The worker receives no session, CSRF, WebAuthn, share, provider credential, bucket, raw provider key, or arbitrary filesystem authority. Capability values are passed through a protected pipe or inherited descriptor, never the command line, normal environment, logs, metrics, traces, crash reports, or process titles.

Output is accepted only when it is one declared static `image/webp` variant with valid WebP signature, display-aspect-preserving dimensions, pixel count, byte size, checksum, and recipe identity. JPEG, PNG, extra output, symbolic links, directories, active media, video output, or mismatched metadata fail the operation.

The preview service remains failure-isolated after successful startup. A missing video binary/library in an image that packages or is configured for `video` is a startup build-integrity error. An image-only profile is valid only when `video` is not configured.

## 9. Deterministic proof and acceptance

Fixtures cover at least valid MP4 and WebM, short video, rotation, duration, blank opening frames, unsupported codec, audio-only content, malformed/truncated structures, huge declared dimensions/duration, invalid offsets, timeouts, worker crash, source-version change, and lifecycle-deleted posters.

Tests prove:

- the base container contains no video runtime files or video-only dependency closure;
- the video container publishes the declared capability and exact dependency inventory;
- both containers accept the same configuration schema and reject capability values they do not package;
- image-only startup fails with a sanitized error when `video` is configured;
- a video file uses the square-grid video icon without artifact lookup or source reads when `video` is not configured;
- excluded and unconfigured videos cause zero source reads;
- exact policy boundaries and explicit Generate/Regenerate behavior match v1.1;
- representative selection is deterministic;
- outputs are WebP-only static raster artifacts with metadata stripped and source display aspect ratio preserved;
- duration/dimensions are bounded and safe;
- Play original is explicit, exact-version, range-capable, no-store, and CSP constrained;
- decoder crash, timeout, corrupt media, and partial output do not affect file APIs or readiness;
- cross-user, disabled-owner, moved, replaced, trashed, deleted, and stale-version cases fail closed;
- the virtualized grid and viewer remain accessible and responsive; and
- full offline Nix, race, fuzz, security, coverage, OCI, and release gates pass for both profiles.

Acceptance criteria:

**VP-001** — v1.2 publishes image-only and video-enabled official container/release outputs with the same configuration schema and API schema.  
**VP-002** — Video-only dependencies and their image-size delta are absent from the base closure and completely inventoried in the video closure.  
**VP-003** — Configured `video` in a profile without the packaged generator or required dependencies fails startup with a sanitized error.  
**VP-004** — Video files use `icon.file.video` without artifact lookup or source retrieval when `video` is not configured; missing active-profile posters use the icon while regeneration proceeds or fails.  
**VP-005** — Valid supported MP4 and WebM fixtures produce deterministic WebP-only posters that preserve display aspect ratio plus bounded duration/dimension metadata.  
**VP-006** — Automatic policy exclusion, off-screen state, unsupported codecs, and unconfigured video capability retrieve zero source bytes.  
**VP-007** — Explicit generation bypasses only automatic age/size policy and remains exact-version, bounded, idempotent, and owner-authorized.  
**VP-008** — Explicit original playback is range-capable, non-autoplaying, CSP constrained, and safely falls back when unplayable.  
**VP-009** — Hostile media, resource exhaustion, dependency crashes, and partial artifacts remain isolated from ordinary EndlessFS operation.  
**VP-010** — All v1 and v1.1 acceptance evidence remains green for every v1.2 profile.

## 10. Feature-completion checklist

- [ ] Video dependencies are absent from the base/image-only build closure.
- [ ] Video-enabled Nix, OCI, and release outputs publish complete capability and dependency inventories.
- [ ] Profile switching uses the same configuration schema and preview store, requires capability values to match the selected build, and needs no migration.
- [ ] Configured generator or dependency absence fails startup with a sanitized error.
- [ ] Unconfigured video files use `icon.file.video` without artifact lookup or source reads.
- [ ] Minimum MP4 and WebM support and exact packaged codecs are documented.
- [ ] Container, track, codec, bounds, signature, and version validation fail closed.
- [ ] Deterministic bounded representative-frame selection is implemented and tested.
- [ ] Video output is static WebP-only imagery preserving display aspect ratio; no playable transcode is created.
- [ ] Duration and dimensions are safe, bounded, and stripped of identifying tags.
- [ ] Explicit playback uses fresh exact-version range capabilities and never autoplay.
- [ ] Decoder process, resource, capability, output, CSP, and log boundaries pass adversarial tests.
- [ ] Automatic exclusions and capability absence prove zero source reads.
- [ ] Browser fallback, metadata, viewer, keyboard, responsive, and theme tests pass.
- [ ] Full v1, v1.1, v1.2, Nix, race, fuzz, coverage, security, OCI, and release evidence is green.

The v1.2 video profile is complete only when its specialized output is genuinely packaged and tested. A video icon is correct behavior when `video` is not configured or a particular source is unsupported. Configuring `video` without its packaged generator is a startup error, not a fallback condition.
