# EndlessFS v1 implemented threat model

This review applies the normative threat model in [v1 specification section 17](./v1-specification.md#17-threat-model) to the provider-portable, multi-replica v1 implementation and locally qualified GCS adapter. It is not a claim about an untested live deployment.

## Boundary review

| Boundary or asset | Implemented controls and evidence | Residual risk |
|---|---|---|
| User files and owner isolation | Private scopes are derived from the authenticated session; public APIs accept only canonical `UserPath` values; raw provider keys are absent. The cross-user endpoint matrix, reserved/encoding corpus, provider contracts, and scope fuzz targets prove success and denial paths. | Logical silos are not cryptographic separation. A compromised process or operator is outside this boundary. |
| Browser to control plane | Stateful hashed sessions, host-only `HttpOnly`/`SameSite=Strict` cookies, CSRF, exact-origin checks, strict JSON, request limits, safe problems, security headers, and no-store capability responses are tested. | A compromised same-origin browser context can act during the session lifetime. |
| Browser to provider data plane | Upload/download capabilities are short-lived, exact-method/object/destination bound, generation-bound for downloads, CORS-bound to the exact application origin, and exercised on a separate instrumented listener. GCS resumable session URLs are encrypted in expiring transient leases, can move between replicas, and are drained before checkpoint closure. | A stolen unexpired capability remains bearer authority until expiry; local protocol qualification cannot prove a live bucket's IAM/CORS configuration. |
| Generated preview plane | v1.1 reauthorizes the exact live owner/path/version before each artifact capability; source reads and WebP writes are byte/dimension/pixel/time/concurrency bounded; artifacts are fully decoded, static-frame checked, metadata-free, path-free, immutable, and held in an independently faultable store. Durable storage uses HMAC-opaque names, CAS visibility, fenced multi-replica claims, provider-neutral size/CRC32C assertions, and exact-generation signed reads over the shared object-store boundary. GCS can attest to the expected CRC32C from metadata without a control-plane body download. Direct-provider browser reads verify manifest SHA-256 plus exact WebP type and signature before display. Automatic policy exclusions read zero source bytes. Codec/store startup probes, malformed-input fuzzing, runtime-loss readiness, credential-free GCS protocol qualification, and 10,002-item browser virtualization are exercised locally. | CRC32C is transport integrity rather than collision resistance; the browser's SHA-256 check supplies end-to-end cryptographic validation. Image decoding remains an in-process attack surface. The protocol fake cannot prove live bucket IAM, CORS, lifecycle, signing, or availability, and a compromised process can access both configured stores. |
| Passkey identity and one-time links | An established pinned WebAuthn library requires discoverable credentials and user verification. Ceremonies and bootstrap/invite/recovery records are expiring, browser/type bound, hash-at-rest, and atomically consumed. See the focused [WebAuthn adapter threat review](./webauthn-threat-review.md). | Lost passkeys require another passkey or an administrator-issued recovery link. There is deliberately no email, password, backup-code, or OAuth fallback. |
| Administrator invariants | Roles are separate from profiles; concurrent CAS tests preserve at least one enabled administrator; disable and recovery revoke sessions and stop owned shares from issuing new capabilities. | Previously issued provider capabilities live until their short expiry. A malicious operator remains trusted infrastructure. |
| Public shares and original previews | Random tokens are hash-at-rest and returned once; subtree resolution is confined and fuzzed; public errors are generic. Only signature-validated raster, bounded UTF-8 text, and PDF can use the explicit original-preview path; active/unknown types are attachments. Public shares cannot trigger generated-preview work. | Browser image/PDF decoder defects and intentional sharing by the owner remain browser/user risks. |
| Untrusted names and content | The UI creates text nodes for untrusted values, never uses untrusted HTML, embeds all application assets, and runs under a restrictive CSP with `nosniff` and no referrer. Chromium origin capture rejects unexpected requests. | Unicode confusables can mislead a person without escaping authorization. |
| Theme build input | The closed Theme API accepts typed data and allowlisted static media only. Archive, media, SVG, inheritance, contrast, digest, and reference validation run before embedding; runtime selection cannot parse archives or add origins/code. | Restricted font/image decoders remain browser attack surface. Operator-selected branding is not an authenticity boundary. |
| State integrity and concurrency | Every replica uses the canonical two-read admission barrier, durable intent, native conditional requests, immutable preparation, a single logical visibility point, and monotonic fences. Deterministic crash/takeover and stale-worker schedules prove that lease expiry enables one CAS takeover but never releases authority by itself. | A failed owner can delay one resource and checkpoint closure until expiry/recovery. This is intentional consistency-over-availability behavior. |
| Provider portability and cutover | Authoritative records exclude provider identifiers and capabilities. A closed-gate checkpoint hashes the exact portable key/body inventory; tests raw-copy it across independent native-version domains, verify read-only, reopen at a new epoch, and continue state/filesystem mutations. | v1 supports quiescent cutover, not online dual writes or reconciliation of mutations performed outside EndlessFS. Operators must retain provider-independent secrets. |
| GCS authentication and protocol | Runtime construction uses the official GCS client with ADC, supports attached workload identity or external WIF/service-account impersonation, and uses keyless IAM `signBlob` discovery for V4 URLs. Credential-free local tests cover generations, checksums, resumability, CORS, error mapping, and lost success. | Bucket IAM, CORS, retention, region, service-account impersonation, and `signBlob` must be validated against a disposable live bucket before production use. |
| Logs and errors | Central structured logging redacts sensitive field families at every level. Request logs use route templates, coarse results, IDs, and durations rather than queries, bodies, full paths, or authorization material. Adversarial and fuzz tests cover the redactor. | Operators control log sinks, and even pseudonymous/coarse operational data has privacy value. |
| Supply chain and release | Nix locks the Go source, fixed-output Go module closure, actions, and official vulnerability database. Module licenses are inventoried, source constraints scanned, the OCI filesystem inspected, and artifacts hashed. | Scanning and reproducibility do not establish absence of unknown upstream vulnerabilities. |

## Privacy and network review

The production binary contains no telemetry, analytics, updater, license check, external identity client, remote theme registry, CDN asset, service worker, SQL client, cache, or queue integration. Required tests construct only explicit loopback control/data listeners. The GCS fake is protocol-level and cannot reach GCP metadata, token, IAM, or storage endpoints. Nix derivation tests use the fixed-output module closure and pinned inputs and have no cloud credential, database, container-daemon, or Internet dependency.

## Claims deliberately excluded

EndlessFS v1 does not claim end-to-end encryption, cryptographic user isolation, defense against a malicious operator/host/provider, complete denial-of-service resistance, production durability, live GCS interoperability, or production readiness. The deterministic memory and local GCS protocol backends prove the provider-neutral contracts and browser/control/data-plane boundaries.

The GCS adapter still requires the opt-in live interoperability, real CORS, signing, identity, fault, deployment, operations, and security review described in specification section 23 before it can be called production-ready.
