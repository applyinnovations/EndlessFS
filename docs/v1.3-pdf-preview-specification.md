# EndlessFS v1.3 PDF Preview Profile Specification

**Status:** Deferred draft; revise after v1.1 implementation  
**Audience:** Implementation agents, maintainers, operators, reviewers, and security testers  
**Normative language:** “MUST”, “MUST NOT”, “SHOULD”, and “MAY” are requirements terms.  
**Target release:** v1.3  
**Inherits:** [`v1-specification.md`](./v1-specification.md), [`v1.1-media-preview-specification.md`](./v1.1-media-preview-specification.md), and the build-profile compatibility rules in [`v1.2-video-preview-specification.md`](./v1.2-video-preview-specification.md)

---

## 1. Executive contract and precedence

EndlessFS v1.3 adds an optional PDF-generation profile to the v1.1 preview architecture. It creates a static first-page image and bounded page metadata. It does not modify the PDF, execute PDF actions, fetch PDF external resources, perform OCR, or replace the existing explicit native-browser PDF viewing path.

This document is a delta specification. Every v1 and v1.1 requirement continues to apply. The v1.2 build-profile compatibility and optional-dependency principles also apply, but a PDF-only v1.3 container is not required to contain the v1.2 video runtime. Build capability profiles are composable rather than cumulatively mandatory.

The base image-only container remains supported. PDF dependencies exist only in PDF-enabled official outputs. Official profiles share one configuration schema and preview-store layout, but `ENDLESSFS_PREVIEW_FORMATS` MUST match the selected profile. Configuring `pdf` in a build without the PDF renderer is a startup error. Switching profiles requires no state migration, bucket rewrite, or regeneration of unrelated previews.

---

## 2. Scope

v1.3 includes:

- a separately packaged PDF renderer and its pinned runtime dependencies;
- a static first-page preview written through the v1.1 artifact-store contract;
- WebP-only output using the configured v1.1 resolution variants;
- safe page count and first-page dimensions where available within bounds;
- continued explicit native-browser PDF viewing through a fresh exact-version capability;
- automatic and explicit generation governed by v1.1 policy and resource limits;
- capability discovery and strict startup validation across build profiles;
- deterministic local fixtures including hostile and structurally complex PDFs; and
- independent PDF and combined-media OCI/release outputs with size, dependency, license, and vulnerability evidence.

v1.3 does not include:

- OCR, text extraction, text indexing, annotations, form filling, JavaScript execution, embedded-file extraction, signature validation, accessibility-tree extraction, document conversion, or per-page gallery generation;
- password collection or decryption of encrypted PDFs;
- remote render services, runtime-downloaded renderers, host-installed dependency assumptions, or arbitrary commands;
- search. A future search feature may add PDF metadata or content indexing under its own specification; and
- any requirement that the PDF-only build include video dependencies.

---

## 3. Build and container outputs

v1.3 adds the following outputs while preserving all earlier outputs:

| Nix output | Packaged capabilities | Required contents |
|---|---|---|
| `.#container` | `image` | Minimal image-only base; no PDF or video runtime. |
| `.#container-video` | `image,video` | v1.2 video profile; no PDF runtime required. |
| `.#container-pdf` | `image,pdf` | Image generation plus the pinned closed PDF renderer. |
| `.#container-media` | `image,video,pdf` | Combined profile with both specialized dependency closures. |
| `.#release-pdf` | `image,pdf` | PDF-profile release artifacts and evidence. |
| `.#release-media` | `image,video,pdf` | Combined-profile release artifacts and evidence. |

The PDF and combined containers MAY contain pinned native renderer binaries or shared libraries. The same restrictions established for video dependencies apply: application code and orchestration remain Go; dependencies are build-time fixed, closed, non-downloadable, non-configurable by path, least-authority, resource bounded, and absent from profiles that do not declare them.

Release evidence MUST make the incremental compressed and unpacked size of the PDF closure and combined closure visible. Shared transitive dependencies are counted accurately rather than double-counted.

The application binary and browser assets expose the same HTTP/configuration schema in every profile. Only the compile-time capability manifest and packaged dependency inventory differ.

## 4. Capability and configuration compatibility

The v1.1 environment schema is unchanged. `ENDLESSFS_PREVIEW_FORMATS` recognizes `pdf` in every official build.

- In `container-pdf` and `container-media`, configured `pdf` becomes active only after packaged renderer and dependency integrity checks pass.
- In image-only or video-only containers, explicitly configured `pdf` is a startup error.
- A PDF uses `icon.file.pdf` without artifact lookup or source retrieval when `pdf` is not configured.
- Missing, stale, corrupt, or lifecycle-deleted PDF artifacts in an active PDF profile use `icon.file.pdf` while policy permits regeneration or reports failure.
- Switching profiles requires an accurate `ENDLESSFS_PREVIEW_FORMATS` value but no migration, preview-store rewrite, preprocessing, or regeneration of image/video artifacts.

The capability manifest records the PDF renderer recipe and renderer dependency version separately. A renderer upgrade changes the recipe identity; it does not invalidate or overwrite older immutable artifacts, though new requests prefer the current compatible recipe.

## 5. Input validation and rendering rules

PDF generation applies only to a provider-validated `application/pdf` source whose worker independently confirms a valid PDF signature and parses a bounded document structure.

The renderer:

- opens the exact authorized source version through bounded sequential or range reads;
- operates without network access or external resource resolution;
- never executes JavaScript, actions, launch instructions, embedded programs, multimedia, forms, or arbitrary URI handlers;
- never extracts or writes embedded files;
- uses only packaged fonts and document-embedded font data permitted by the renderer’s safe bounded mode;
- renders the first display page only;
- applies the page rotation and crop/media box rules defined by the versioned recipe;
- constrains decoded/rasterized dimensions, total pixels, objects, recursion, streams, fonts, images, time, memory, file descriptors, and output bytes;
- strips document metadata from the artifact; and
- returns no source text or arbitrary metadata.

The generator rejects or safely terminates on:

- malformed headers, cross-reference structures, object streams, incremental updates, page trees, or bounds;
- cyclic, excessively deep, excessively large, or contradictory structures;
- encryption or password protection;
- unsupported filters or color spaces that cannot be processed safely;
- external references or resources;
- invalid, negative, non-finite, or excessive page geometry;
- decompression, image, font, object-count, or parser bombs;
- renderer crash, timeout, unexpected files, or mismatched output; and
- a source version change during processing.

Encrypted/password-protected, malformed, unsupported, or resource-excessive PDFs retain the PDF icon, safe metadata, explicit Download, and existing browser-native preview where the browser can handle the original. EndlessFS does not request a password.

---

## 6. Artifact and metadata behavior

The default PDF recipe renders the first display page against an application-defined neutral background when transparency requires composition. It produces the v1.1 requested maximum-edge variants without upscaling beyond useful raster detail.

Output is static lossy WebP at quality `82` through the single pinned v1.3 encoder. The artifact preserves the first page's display aspect ratio without crop, stretch, or padding in the artifact. JPEG, PNG, PDF, active content, animation, document metadata, attachments, text layer, links, forms, scripts, and source profiles beyond what is required for correct sRGB display are prohibited.

Safe optional manifest metadata is:

```text
pageCount
firstPageWidthPoints
firstPageHeightPoints
```

Page count is returned only when the renderer can determine it within the bounded parse budget. Width and height are finite positive bounded values derived from validated page geometry. Title, author, subject, keywords, creator, producer, timestamps, file paths, embedded filenames, annotations, form values, signature identities, and arbitrary document-info fields are not returned.

Page count or geometry failure MUST NOT prevent a successfully validated first-page raster from being used; missing optional metadata is represented as absent rather than guessed.

## 7. Browser behavior

PDF tiles use `icon.file.pdf` until a ready first-page artifact is available. Lazy automatic generation obeys all v1.1 viewport, policy, format, and concurrency rules.

The full-viewport viewer:

- displays a ready generated first-page image immediately where available;
- shows bounded page count and geometry only when available and useful;
- provides View original and Download actions;
- retains the existing browser-native PDF iframe path through a fresh exact-path/version inline capability;
- does not load the original until the user explicitly chooses View original;
- preserves the existing restrictive `frame-src`, capability, no-referrer, and `nosniff` behavior;
- falls back to the generated page, PDF icon, metadata, and Download if native viewing is unavailable; and
- uses the same previous/next, keyboard, focus, responsive, and live-status contract as v1.1.

The generated first-page image is a convenience preview and is never presented as a complete rendering, accessibility representation, or validation of the PDF.

## 8. Security and runtime isolation

The PDF parser/renderer is a hostile-input boundary and MUST run through a one-operation isolation boundary unless an approved library provides equivalent in-process safety with explicit maintainer review. The specialized runtime receives no application/provider credentials and only the exact bounded source/output authority needed for one operation.

Capability secrets are passed through protected pipes or inherited descriptors, never arguments, normal environment, process title, logs, metrics, traces, crash reports, temporary filenames, or renderer diagnostics.

If temporary storage is required by the chosen renderer, it MUST be an operation-unique bounded runtime directory or anonymous file created by the Go supervisor, inaccessible to HTTP paths, cleared on completion, and unnecessary for authoritative state. It cannot be a required persistent volume. Tests prove cleanup after success, failure, timeout, and process termination.

Output validation accepts only one declared static `image/webp` variant with exact WebP signature, page-aspect-preserving dimensions, byte size, pixel count, checksum, and recipe identity. JPEG, PNG, PDF, PostScript, SVG, HTML, XML, video, executable, archive, extra file, link, directory, or mismatched output fails the operation.

After successful startup, renderer or preview-store failure remains isolated from authoritative file data but makes preview requests unavailable and `/readyz` unhealthy. A build that packages or is configured for `pdf` but cannot validate its renderer is a startup build-integrity error. A profile without PDF support is valid only when `pdf` is not configured.

## 9. Deterministic proof and acceptance

Reviewed fixtures include at least a simple one-page PDF, multipage PDF, rotated/cropped page, transparency, embedded font/image, incremental update, encrypted PDF, malformed/truncated structures, cyclic/deep page tree, oversized geometry, excessive object/stream counts, decompression bombs, active actions/JavaScript/external references, worker timeout/crash, source-version change, and lifecycle-deleted artifacts.

Tests prove:

- PDF dependencies are absent from image-only and video-only closures;
- PDF and combined containers declare exact capabilities and complete dependency inventories;
- every profile accepts the same environment schema and rejects configured capabilities it does not package;
- image/video-only startup fails with a sanitized error when `pdf` is configured;
- PDFs use the square-grid PDF icon without artifact lookup or source reads when `pdf` is not configured;
- excluded, off-screen, unsupported, encrypted, and unconfigured PDFs cause zero automatic source reads where the decision can be made from trusted metadata/capabilities;
- first-page selection and geometry are deterministic;
- outputs are WebP-only static rasters preserving first-page aspect ratio with metadata and active content absent;
- optional page metadata is bounded and contains no identifying document-info values;
- original viewing remains explicit, exact-version, no-store, and CSP constrained;
- renderer crash, timeout, temporary-file cleanup, malformed input, and partial output do not affect file APIs or readiness;
- cross-user, disabled-owner, moved, replaced, trashed, deleted, and stale-version cases fail closed;
- browser icons, viewer, navigation, keyboard, responsive, and theme behavior pass; and
- the full offline Nix, race, fuzz, security, coverage, OCI, dependency, and release gates pass for all four profiles.

Acceptance criteria:

**PP-001** — v1.3 publishes image-only, video-enabled, PDF-enabled, and combined official container outputs with the same configuration schema and API schema.  
**PP-002** — PDF-only dependencies and size delta are absent from image/video-only closures and completely inventoried in PDF-enabled closures.  
**PP-003** — Configured `pdf` in a profile without the packaged renderer or required dependencies fails startup with a sanitized error.  
**PP-004** — PDFs use `icon.file.pdf` without artifact lookup or source retrieval when `pdf` is not configured; missing active-profile artifacts use the icon while regeneration proceeds or fails.  
**PP-005** — Valid PDF fixtures produce deterministic WebP-only first-page variants preserving page aspect ratio and safe bounded optional page metadata.  
**PP-006** — Encrypted, malformed, unsupported, excluded, off-screen, and unconfigured PDF cases fall back without weakening source-read or resource policy.  
**PP-007** — Explicit generation bypasses only automatic age/size policy and remains exact-version, bounded, idempotent, and owner-authorized.  
**PP-008** — PDF actions, JavaScript, external resources, attachments, forms, and document-info metadata never execute or cross into artifacts/API output.  
**PP-009** — Explicit original viewing remains capability-bound, no-store, CSP constrained, and independent from generated preview availability.  
**PP-010** — Hostile PDFs, resource exhaustion, dependency crashes, partial outputs, and temporary files remain isolated from ordinary EndlessFS operation.  
**PP-011** — All v1, v1.1, applicable v1.2 profile, and v1.3 acceptance evidence remains green for every published profile.

## 10. Feature-completion checklist

- [ ] PDF dependencies are absent from base/image-only and video-only build closures.
- [ ] PDF and combined Nix, OCI, and release outputs publish complete capability, size, dependency, and license inventories.
- [ ] Profile switching uses the same configuration schema and preview store, requires capability values to match the selected build, and needs no migration.
- [ ] Configured renderer or dependency absence fails startup with a sanitized error.
- [ ] Unconfigured PDFs use `icon.file.pdf` without artifact lookup or source reads.
- [ ] PDF signature, structure, page, bounds, filter, font/image, resource, and exact-version validation fail closed.
- [ ] JavaScript, actions, forms, attachments, external references, and arbitrary metadata never execute or escape.
- [ ] Encrypted/password-protected PDFs require no password and fall back safely.
- [ ] Deterministic first-page rendering produces WebP-only variants preserving page aspect ratio.
- [ ] Page count and geometry are optional, bounded, and free of identifying document metadata.
- [ ] Explicit native original viewing remains exact-version, no-store, CSP constrained, and user initiated.
- [ ] Renderer process, temporary storage, capability, output, logging, and cleanup boundaries pass adversarial tests.
- [ ] Automatic exclusions and capability absence prove zero unintended source reads.
- [ ] Browser fallback, viewer, navigation, keyboard, responsive, and theme tests pass.
- [ ] Full v1, v1.1, applicable v1.2, v1.3, Nix, race, fuzz, coverage, security, OCI, and release evidence is green.

The v1.3 PDF profile is complete only when its specialized outputs are genuinely packaged and tested. A PDF icon is correct behavior when `pdf` is not configured or a particular document is unsupported. Configuring `pdf` without its packaged renderer is a startup error, not a fallback condition.
